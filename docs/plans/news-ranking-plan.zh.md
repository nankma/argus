## 一、讓本文重新定調的線上事故（2026-08-18）

這段是在下方調研完成後隔天補上的，而且它改變了最終建議該長什麼樣，所以
放在最前面。

**現象**：操作者回報，最近一次推送的內容幾乎全部來自同一個新聞源。

**根本原因**：`news_push.select_candidate_articles` 把整個快取**只按發布
時間排序**，然後每個主題取前 N 篇。**整條挑選路徑上完全沒有任何來源多樣性
約束**。誰發文最勤，誰就整碗端走「最新」那一段。

**線上實測數據**（生產環境 VM，快取共 1262 篇）：

| 來源 | 佔全部快取 | 佔**最新 50 篇** |
|---|---|---|
| `hackernews` | 33%（422 篇） | **64%（32 篇）** |
| `engadget` | 3.8% | 12% |
| `marketwatch` | 3.5% | 10% |
| 其餘 17 個來源合計 | 約 55% | 14% |

Hacker News 的 `search_by_date` 回傳的是**持續不斷的新投稿流**（每小時數十
篇），而一般 RSS feed 一天才發 10-30 篇。在純粹按時間排序的挑選邏輯下，
HN 光靠發文頻率就贏了。

**為什麼現在才浮現。** 這個缺陷一直都在——挑選邏輯從來就只看時間。但在
2026-08-16 之前，每個來源每輪最多只抓 5 篇，**那個低上限意外地把來源分布
拉平了**，掩蓋了問題。上限調高之後（RSS 5→200、可查詢來源 5→50，見
`local-news-cache-plan.md` item 7），這層意外的保護消失了：快取池開始如實
反映各家真實發文頻率，HN 就壓倒性勝出。上限調高本身是有效的——最後一次
推送的候選文章有 26 篇，比原本的約 5 篇多得多——但它用來源多樣性換來了
數量。

**同一個發現裡還有第二層問題。** `fetch_hackernews` 刻意使用
`search_by_date`（原因見 `ai-news-sources.md`），所以拿到的是**最新的投稿
——也就是還沒有人投票的那批**（實測分數為 2、2、1）。因此現在不只是 HN
獨占，而且獨占的是 **HN 裡最沒經過社群篩選的那一塊**。這與下方第 1b 節
「HN 的 `points`/`num_comments` 被丟棄」是同一個問題的一體兩面。

**狀態：刻意維持現狀運行。** 操作者決定先讓現行行為跑約 2 天，觀察真實
影響後再動手，而不是反射性地打補丁。診斷本身沒有任何不確定性；待確認的是
它在實務上到底把推送品質拉低了多少——這個答案值得在選定下方方案前先取得。

**這件事對設計的啟示**，也是它該寫進本文而非單獨開一張 bug 單的原因：它
直接證明了**「時間新舊」本身不是一個排序函數**。任何值得採用的評分機制，
都必須同時編碼「很多家媒體獨立報導了這件事」（第 1b 節的跨源印證）與
「單一來源不該塞滿整份推送」（多樣性作為顯式約束）。這是兩件不同的事，
而目前兩者都不存在。

## 二、「重要性」的三種定義傳統

### 2a. 新聞學理論——編輯口中的「新聞價值」

奠基性的分類法是 **Galtung & Ruge（1965）**，後由 **Harcup & O'Neill
（2001，2017 再修訂）** 更新，是新聞學研究中被引用最多的框架，也是多數
「重要性」直覺背後真正想表達的詞彙。Harcup & O'Neill 修訂後的清單：

| 新聞價值 | 意義 |
|---|---|
| **影響規模** | 影響多少人、多少金額 |
| **切身相關** | 與受眾自身生活／利益的關聯 |
| **意外性** | 出乎意料、偏離常軌 |
| **權力精英** | 涉及有影響力的組織或人物 |
| **名人** | 涉及本來就出名的個人 |
| **壞消息／好消息** | 衝突、失敗、災難／救援、突破 |
| **後續進展** | 推進受眾腦中已有的故事線 |
| **娛樂性** | 人情趣味、奇聞 |
| **媒體自身議程** | 符合該媒體本身的優先關注 |

**這對我們的意義**：這些都是人類編輯實際在用的判準，也正因如此，它們是
**能用文字寫進 prompt 的**——而點擊率模型那類東西無法這樣描述。其中數項
直接對應本專案的領域（影響規模、意外性、權力精英、後續進展），另外數項
明顯不適用（名人、娛樂性）。

### 2b. 計算信號——不需要模型，從資料推斷重要性

這些是實際運行中的新聞聚合器主要依賴的東西。以下按對**本專案**的適用度
排序。

| 信號 | 運作方式 | 這裡適用嗎 |
|---|---|---|
| **跨源印證** | 統計有多少**獨立**媒體報導了同一件事。實務上最強的重要性代理指標——多個編輯獨立判斷某事重要，是很難偽造的真實信號 | **適用，而且免費。** 21 個來源本來就每輪拉進同一個快取。需要故事聚類（見下），但不需要新資料 |
| **突發檢測** | 某詞彙／實體的出現頻率相對自身近期基線突然飆升。經典事件檢測手法，通常與聚類搭配 | **適用，成本低。** 48 小時快取足以做粗糙基線；要做得正確則需要更長的保留期 |
| **來源權威度** | 依媒體信譽加權。Google News 明確列出這一項（authoritativeness），與 prominence、freshness 並列 | **適用，且極簡單**——但只能手工指定每個來源的權重（路透 > 某數碼部落格）。沒有連結圖譜可供正確計算 |
| **時效衰減** | 分數隨時間衰減；突發新聞勝過隔天的同一則 | **適用**——`published_dt` 已經解析並儲存 |
| **互動／社群信號** | 讚數、留言數、分享數 | **部分適用——而且目前有免費資料被丟棄。** 見下方發現 |
| **實體顯著度** | 某大公司／人物是故事**核心**，還是只被順帶提及？ | 可行，但需要 NER 或額外一次 LLM 呼叫。投入產出比較低 |
| **連結／引用圖譜** | 類 PageRank，看媒體之間互相引用 | **不適用。** RSS 不提供連結圖譜 |

**撰寫本文時實測確認的具體發現**：Hacker News 的 Algolia API 每一筆結果都
會回傳 `points` 與 `num_comments`，而 `news_sources.fetch_hackernews`
**把兩者都丟棄了**——它只映射標題、連結、來源、摘要與日期。這是一個已經
抓進來卻被扔掉的互動信號，零額外 API 成本。

**同樣實測確認的重要但書**：`fetch_hackernews` 使用 `search_by_date`
（刻意如此，見 `ai-news-sources.md`），所以回傳的是**最新**投稿，這些投稿
根本還沒累積到票數。實測樣本的分數是 2、2、1。票數要在文章發布數小時後才
有意義，因此這個信號適用於**後續輪次對快取文章重新評分**，而不適合在首次
抓取時使用。把它當成即插即用的重要性數值之前，必須知道這件事。

### 2c. LLM 當裁判

目前已是相當成熟的評估範式，有三種標準形態：

| 形態 | 做法 | 取捨 |
|---|---|---|
| **逐條評分（pointwise）** | 每篇獨立給分（如 1-5 分李克特量表） | 最便宜、最好擴展；分數在不同批次間會漂移，因此絕對閾值不穩定 |
| **兩兩比較（pairwise）** | 「這兩篇哪篇更重要？」 | 單次判斷最可靠；需 O(n²) 次比較，在任何實際量級下都太貴 |
| **整批排序（listwise）** | 把整份候選清單交給模型，取回排序結果 | 整批只需一次呼叫；清單一長品質就下降 |

關於 LLM 在細粒度序數量表上做絕對（逐條）相關性判斷的研究指出，這種做法
可行但對量表設計相當敏感——這與本專案自己得來不易的教訓一致：**結構化
輸出、一個問題一個欄位，勝過要求模型給一個籠統的綜合分數**
（`system-overview.md` 附錄 B.1：結構化輸出版本得 15/15，而精簡的純文字
prompt 版本只得 1/15）。

## 三、「這位使用者想看什麼」怎麼找

| 方法 | 運作方式 | 這裡適用嗎 |
|---|---|---|
| **內容過濾** | 用使用者按讚／填寫的內容建立檔案，再比對文章內容 | **適用——這就是目前已建好的做法**（`news_classify.py` 的 13 個分類 + 使用者填寫的興趣） |
| **協同過濾** | 「和你相似的使用者也讀了 X」 | **不適用。** 結構上不可能——需要大量使用者的重疊歷史，本部署只有寥寥數人。而且它對新項目有已知的冷啟動問題，而新聞裡**每一則**都是新項目 |
| **混合式** | 協同 + 內容，業界標準生產架構 | **不適用**——協同那半邊根本不存在 |
| **語義嵌入（embeddings）** | 把文章與使用者興趣檔案嵌入同一向量空間，按餘弦相似度排序。Sentence-BERT 式做法。這正是學界對冷啟動的標準答案，因為它完全不需要互動歷史 | **適用——是目前最值得的升級**，遠勝現在粗糙的 13 分類比對。「AAOI」或「光纖元件」無法用 13 個分類表達，但可以用向量表達 |
| **隱式回饋** | 點擊、停留時長、開啟率 | **不適用，而且這是真正的結構性缺口**——Telegram 推送沒有任何點擊或已讀信號回傳。現有架構無法觀測到推送是否被閱讀，遑論是否被喜歡 |
| **顯式回饋** | 讚／倒讚、逐則評分 | **適用且加起來很便宜**——Telegram 行內按鈕。由於隱式回饋不可得，這是本專案唯一可能取得偏好信號的實際途徑 |

**一句話總結**：幾乎所有現代新聞推薦研究都預設有一條本專案產生不出來的
點擊流。剩下可用的——也是這個規模下真正合適的——就是內容比對（用 embeddings
大幅提升精準度），外加顯式回饋（如果值得為它加一顆按鈕）。

## 四、該推幾條（原始問題）

| 方法 | 運作方式 | 取捨 |
|---|---|---|
| **固定 top-N** | 永遠推 N 條 | 目前的做法。簡單；但冷清的日子推湊數的、熱鬧的日子被截斷——正是這次的抱怨 |
| **絕對閾值** | 分數高於固定門檻就推 | 天然變長度。但 LLM 分數的絕對校準會漂移，因此很脆弱 |
| **相對／自適應閾值** | 門檻由**近期分數分布**決定，例如「近 7 天的前 10%」。這是告警系統的標準做法，正是為了避免固定門檻造成的告警疲勞 | 自我校準；需要保留分數歷史（本專案快取 TTL 只有 48 小時，所以需要一張小的持久化分數表） |
| **閾值 + 上下限夾逼** | 自適應閾值，但夾在最少 2 條、最多約 12 條之間 | 同時防住兩種失效：不會空得尷尬，也不會變成一面文字牆。Telegram 的 4096 字元上限讓「上限」成為必要機制，不是裝飾 |
| **邊際效用截斷** | 當下一條相對已收錄內容增益很小時就停（考慮冗餘，MMR 式） | 天生處理「八家媒體報同一件事」的情況。較複雜；目前推送 prompt 中「跨來源綜合」的指示已部分達成此效果 |

## 五、可選方案

以下五個方案各自可獨立決定。它們**不是**必須依序完成的階段——A 是止血、
B/C/D 是各自可單獨採用的真實設計、E 是一個會改變 B 與 D 實作方式的前置
決策。

### 方案 A — 挑選時加入每來源上限（針對本次事故的止血）

在 `select_candidate_articles` 內限制單一來源對一份推送最多貢獻幾篇
（例如 2-3 篇）。

| | |
|---|---|
| **工作量** | 約 10 行，含測試一個下午 |
| **成本** | 零——無 API 呼叫，完全確定性 |
| **能解決** | 來源塌陷症狀，立即見效 |
| **不能解決** | 任何與重要性有關的事。排序信號仍然只有時間新舊，這只是把同樣未經排序的挑選攤到更多來源上 |
| **風險** | 低。最壞情況是日後被 B/D 取代而刪除 |

誠實的定位：這是**症狀修補**，不是排序設計。它的價值在於夠便宜，便宜到
即使日後會被丟棄也值得先做。

### 方案 B — 確定性評分：跨源印證 + 權威度 + 時效

把快取依故事聚類，再對每個聚類評分：（涵蓋該故事的獨立來源數）×（手工
指定的來源權威權重），並隨時間衰減。挑選**分數最高的聚類**，每個聚類取
一篇代表文章。

| | |
|---|---|
| **工作量** | 以天計而非以小時計。需要故事聚類（見方案 E） |
| **成本** | 零經常性成本——評分路徑上沒有 LLM 呼叫 |
| **能解決** | 一次解決兩個問題：既編碼了現實中最強的重要性代理指標，**又**因為以聚類（而非單篇）為單位挑選，讓單一來源獨占在結構上不可能發生 |
| **不能解決** | 「對**這位特定使用者**有趣」——它是全域重要性分數，個人化仍然來自既有的分類過濾 |
| **風險** | 中。聚類品質是成敗關鍵；聚類做不好，印證計數就毫無意義 |

順帶可納入目前被丟棄的兩個免費信號：HN 的 `points`/`num_comments`
（用於後續重新評分，而非首次抓取，理由見第 2b 節但書）。

### 方案 C — 自適應推送數量（字面上回答原始問題）

把固定的 `MAX_ARTICLES_PER_TOPIC` 換成由近期分數分布決定的閾值，並以
上下限夾住。

| | |
|---|---|
| **工作量** | 就其**本身**而言不大——但沒有 B 或 D 就毫無意義，因為它需要一個分數才能設閾值 |
| **成本** | 零經常性成本；需要一張小的持久化分數歷史表（48 小時快取 TTL 太短，無法用於校準） |
| **能解決** | 推送數量真正隨「今天有多少好新聞」浮動 |
| **風險** | 低，**前提是**有上下限夾逼——Telegram 的 4096 字元上限讓「上限」成為必要機制而非裝飾 |

**必須講明的依賴關係**：這是真正回答「別讓 5 成為上限」的方案，但它無法
最先做。它是 B 或 D 所產生分數的消費端。

### 方案 D — 用 LLM 判斷重要性

逐條評分、結構化輸出、**一個判準一個欄位**（影響規模／意外性／權力精英／
與此使用者的相關性），採用第 2a 節 Harcup & O'Neill 的詞彙，而不是問一個
籠統的「重要性 1-10 分」。

| | |
|---|---|
| **工作量** | 中等——呼叫本身很簡單，真正的工作是把評分準則設計對 |
| **成本** | **真實且經常性。** 每個抓取週期至少多一次呼叫 |
| **能解決** | 唯一能判斷「有趣」而不只是「被多家印證」的方案。能處理獨家爆料——那種正因為只有一家有、反而會被方案 B 評低分的情況 |
| **風險** | 最高。LLM 的絕對分數會在批次間漂移，這與方案 C 的閾值機制交互不良。必須實測，不能假設它更好 |

「一個判準一個欄位」的結構化輸出不是風格偏好，而是本專案自己實測出來的
結論（`system-overview.md` 附錄 B.1：精簡單一分數的 prompt 變體得 1/15，
結構化版本得 15/15）。

### 方案 E — 文本相似度：詞彙式、稠密式，或混合式

本方案原本寫成「要不要引入 sentence embeddings」的二選一。**這個框架是錯
的**，已於 2026-08-19 修正——操作者指出 BM25 與嵌入向量是互補的，而且業界
本來就常常一起部署。這裡其實有三個層級，而不是兩個選項，而且**最便宜的那
一層今天就能用**。

**為什麼它們互補而非互斥**（這在資訊檢索領域是定論，不是新主張）：BM25／
TF-IDF 這類稀疏詞彙方法擅長精確匹配——產品代號、股票代碼、專有名詞、罕見
技術術語——但完全處理不了換句話說。稠密嵌入擅長換句話說與概念相似，卻會
低估罕見詞的精確匹配。還有一點對我們特別重要：**BM25 不需訓練就能在
領域外資料上表現良好，而稠密檢索器在與訓練資料不同的資料上會明顯退化。**
業界標準做法是兩者並行執行、再融合排序清單，通常用倒數排名融合 RRF
（`score(d) = Σ 1/(k + rank(d))`，k≈60）——它完全丟棄原始分數、只看排名
位置，正好繞開了方案 D 同樣會遇到的分數校準問題。

**第 1 層 — 詞彙式（TF-IDF／BM25）。今天就能用，零新增依賴。**

本專案環境中 `scikit-learn`、`numpy`、`scipy` **已經安裝好了**（2026-08-19
驗證）。因此 TF-IDF + 餘弦相似度的新增成本是零——不用下載、不用 API、
不需要討論記憶體預算。

**在真實生產快取上實測，2026-08-19**（從線上 VM 取出的 2082 篇文章）：

| 指標 | 結果 |
|---|---|
| 向量化 + 完整兩兩相似度 | **0.96 秒** |
| 記憶體峰值 | **36 MB**——在 1 GB VM 內綽綽有餘（設計原則 P5） |
| 詞彙表 | 16,255 個詞（1-2 gram） |
| 餘弦 ≥ 0.45 的跨來源配對 | 13 組 |

而且它確實找出了真正的同一故事聚類——以下是未經修飾的實際輸出樣本：

- `1.00` BBC Business + Hacker News — *「The critical tech staying safe by going underground」*
- `0.75` GNews + Hacker News — *「Google to buy Spirit Airlines business data for $10M」*
- `0.59`／`0.54` Engadget + TechCrunch + Hacker News — Apple 配備相機的 AirPods（**三個**來源）
- `0.50` Hacker News + TechCrunch — *「Etched's valuation doubles to $21B」*

**第 2 層 — 稠密嵌入。** 帶來任何詞彙方法都做不到的換句話說匹配（兩家媒體
用完全不同的字描述同一事件），並解鎖第三節的語義興趣比對。但它仍然是個
真實決策：在 1 GB VM 上跑本地 sentence-transformer 是實際的記憶體問題，
而嵌入 API 則是新的經常性成本加上抓取路徑上的新依賴。

**第 3 層 — 混合式，以 RRF 融合。** 業界標準答案，也是正確的終局狀態。
但只有在第 2 層存在之後才值得做，因為單獨的第 1 層沒有東西可以融合。

**本方案修正後的建議**：**現在就做第 1 層**——它實質上免費、已經在本專案
自己的真實資料上被實測驗證可行，而且立刻解除方案 B 聚類的阻塞。把第 2 層
當成之後另一個獨立決策，由**第 1 層實際上在哪裡失效**來提供依據（屆時是
看得到的，而不是用猜的），第 3 層則作為之後的終局狀態。

### 實測第 1 層時發現的一個真陷阱——聚合站不等於印證

上面分數最高的那兩組配對（`1.00`，BBC + HN）**是同一篇文章被收錄了兩次**，
而不是兩家媒體各自獨立報導了同一件事：Hacker News 是聚合站，所以一則
連到 BBC 文章的 HN 條目會帶著 BBC 一模一樣的標題。把它算成「2 個來源印證了
這則新聞」會是明確的錯誤，而且會**系統性地灌水給那個本來就已經過度代表的
來源**（見上方來源塌陷事故）。

在快取中確認：**有 16 個標題出現超過一次**，而現有的去重機制抓不到，因為
`news_cache` 是依連結雜湊去重的，而 HN 的連結和 BBC 的不一樣。

這正是姊妹篇調研（`sample-diversity-survey.md`）在抽象層面提出的那個但書的
具體實例——HHI 之類的集中度指標假設被計數的單位彼此獨立，而轉載或聚合的
內容違反了這個假設。**方案 B 中任何印證計數都必須先把聚合站條目歸併回其
原始出處**，否則量到的就是錯的東西。現在知道，好過在推送裡才發現。

**第二個發現，關於這個信號到底有多少量**：2082 篇文章中只有 13 組跨來源
配對達到門檻。在這個量級下，印證是一個**稀疏**信號——真實可用，但它會把
絕大多數文章打成同一分（無印證），因此**方案 B 不能作為唯一的排序信號**。
它能把最頂端那少數幾則從其餘中分離出來，但其餘的排序仍然需要別的東西。

### 刻意不建議的做法

- **協同過濾**——在這個使用者量級下結構上不可能。
- **隱式回饋建模**——沒有點擊信號可供建模，且 Telegram 推送架構本身就
  產生不出來。
- **顯式回饋按鈕**——確實有用且便宜，但這是**產品**決策（操作者願不願意
  讓訂閱者被要求評分？），不是排序決策。值得與上述所有項目分開決定。

### 如果一定要挑一條路

**現在做 A，同時做 E 的第 1 層（免費且已實測可行），然後 B，再來 C。**
D 放到最後，且只在 B+C 被證明不足時才做——它是唯一有經常性成本的方案，而
本專案自身的歷史（附錄 B.1）正是一個直接教訓：聽起來合理的升級，必須先
實測才能信任。E 的第 2 層（稠密嵌入）則變成一個獨立決策，由第 1 層在哪裡
實際不足來提供依據，而不是一開始就決定。

2026-08-19 修正：原本的順序把「決定 E」當成 B 之前的阻塞關卡，前提是假設
E 意味著一次昂貴的嵌入向量承諾。把 E 拆成三層之後這個關卡就消失了——詞彙
層免費、現在就做得到，而且足以解除 B 的阻塞。

但無論如何，**2 天的觀察期都是當下正確的動作**：它不花任何成本，而且能
告訴我們來源塌陷究竟是真的在拉低推送品質，還是只是紙面上看起來不對。
